# Plan Tracker

## 核心职责

1. **创建/更新 Plan 文件**: 在当前项目根目录维护 `PLAN_<名称>.md` 文件
2. **Context 恢复**: 每次 context compact 后，第一件事读取当前 plan 文件恢复上下文
3. **进度同步**: 执行 plan 中的任务时，实时更新 plan 文件中的状态标记

## Plan 文件格式

文件命名: `PLAN_<feature_name>.md`，放在项目工作目录根。

### 必须包含的章节

```markdown
# <Feature> — 标题

## Context
- 背景说明、设计依据（引用设计文档如《模型方案.md》）
- 关键设计点概述

## Step N: <步骤标题> <状态标记>
**File**: `path/to/file` — 操作类型

- 具体实现内容（保留代码片段、接口定义等关键细节）
- 不要只写摘要，保留足够的技术细节以便 context 恢复后能继续工作

## 实施顺序
- 编号列表 + 状态

## 关键文件清单
- 表格: 文件 | 操作 | 状态

## 验证状态
- 表格: 验证项 | 状态

## 遗留项 (Blockers)
- 表格: 项目 | 说明 | 优先级
```

### 状态标记

| 标记 | 含义 |
|------|------|
| (无标记) | 待实现 |
| ✅ | 已完成 |
| ⚠️ | 有问题/需注意 |
| ⏳ | 进行中 |

## 工作流程

### 创建 Plan

1. 分析用户需求，阅读相关设计文档和代码
2. 在工作目录创建 `PLAN_<name>.md`
3. 按上述格式填写所有章节，包含完整技术细节（代码片段、接口签名、维度说明等）

### 执行 Plan

1. 使用 `executing-plans` 按 plan 中的实施顺序逐步执行；本 skill 负责持久状态，不替代实现工作流
2. 每完成一个 Step，更新 plan 文件中对应的状态标记
3. 如果实现中发现 plan 有误（如接口不一致、维度错误），同步更新 plan

### Context Compact 恢复

**这是最关键的场景**。当 context 被压缩后：

1. 首先读取工作目录下所有 `PLAN_*.md` 文件
2. 根据 plan 中的状态标记确定当前进度
3. 对于 ⏳ 或未完成的 Step，读取相关代码文件确认实际状态
4. 继续执行未完成的任务

### 更新 Plan

当用户说"更新plan"：

1. 读取当前 plan 文件
2. 检查每个 Step 对应的代码文件的实际实现状态
3. 更新状态标记、补充遗留项
4. 如果架构有变化（如新增模块），更新 Context 和相关 Step 的描述

## 重要原则

- **保留技术细节**: Plan 不是摘要，而是可以恢复 context 的完整参考。代码片段、维度说明、接口签名都要保留
- **实事求是**: 只标记实际完成的为 ✅，不预先标记
- **Bug 记录**: 实现中发现并修复的 bug 要在对应 Step 中注明（如 `h0.squeeze(0)` → `h0[-1]` 修复）
- **一个 feature 一个 plan**: 不要把多个不相关 feature 混在一个 plan 文件里
- **Plan 是活文档**: 随着实现推进持续更新，不是写完就不管了

## 验证

- [ ] Plan 位于当前项目根目录且文件名为 `PLAN_<名称>.md`
- [ ] 步骤状态与代码/文件的实际状态一致
- [ ] 已完成步骤包含验证证据，未完成项没有被提前标记
- [ ] 新发现的范围变化、风险和 blocker 已同步记录
- [ ] Context 恢复后已核对 ⏳ 与未完成步骤对应的实际文件
